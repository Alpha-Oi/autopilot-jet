# ADR 0005: Development-first publication boundary

## Context

Нужно продолжить upstream-историю `nick-vels/skills` в публичном `Alpha-Oi/skills`, не изменяя стабильную ветку `main` до доказанной готовности. Целевой репозиторий может отсутствовать или появиться до публикации, а глобальная Git identity и передача credential values создают лишний риск для машины и секретов.

## Decision

Вести реализацию в локальной `development`, начинающейся от upstream commit `99c7e73678195cac08080bdd442f0e49a7ccb640`, сохраняя `upstream` на `nick-vels/skills`. Использовать repo-local identity `Alpha-Oi` с подтверждённым GitHub noreply email. Перед публикацией read-only API подтверждает login и состояние `Alpha-Oi/skills`; если репозитория нет, он создаётся Public через активную сессию, а если уже существует, lease-защищённое принудительное обновление допускается только для `refs/heads/development` после чтения remote ref. `main` изменяется только отдельным PR `development -> main` после зелёного CI.

## Why

Разделение локальной реализации, первой публикации и merge защищает `main`, сохраняет происхождение истории и оставляет внешние действия проверяемыми. Repo-local identity достигает нужного авторства без изменения глобальной конфигурации, а lease и предварительное чтение ref ограничивают риск гонки при существующем target.

## Consequences

Первая публикация никогда не обновляет `main`; 100% готовность допустима только после blind acceptance и успешного GitHub Actions run. Create, push, PR и merge остаются внешними gates и выполняются только авторизацией активной сессии `Alpha-Oi`, без извлечения или записи credential values. Если connector не предоставляет создание репозитория, локальная сборка продолжается, но публикация остаётся заблокированной до появления разрешённой операции.
